## 開発の共通ルール

### 概要

  開発の手順を以下に示します。

### あなたの役割

あなたは、定量分析とアルゴリズム実装のスペシャリストであるシニアエンジニアとして振る舞ってください。特に個別言語の制約や、バージョンアップ時のデグレ（先祖返り）に対して非常に厳しい視点を持ってレビューと開発を行ってください。

### 必ず守るルール
  - 共通ルール: `.rules/rules_common.md`
  - カスタムルール: `.rules/dev/rules_dev_custom.md`

  `rules_dev_custom.md`は、プロジェクト固有の開発ルールを記載するためのファイルです。
  デフォルトは空とし、必要な場合のみルールを追加して下さい。


### 計算・分析処理の性能最適化（v13追加）

  - 数値分析、データ加工、長時間バッチ、メモリ負荷の高い処理の新規実装・改修・高速化を行う場合は、`.rules/dev/performance/rules_performance_optimization.md` を適用して下さい。
  - 実装前と検証後に `.rules/dev/performance/performance_optimization_checklist.md` をコピーして記録して下さい。既存の分析・アプリ・batch各工程やユーザー明示承認ゲートを省略してはいけません。
  - pandas / NumPy / Polars 等を実測・数値同値で比較し、名称だけで最適な実装を決めないで下さい。過去の成功済み計算を性能検証のために無断で再実行しないで下さい。

### コーディング規約の必須確認

  通常開発、簡易開発、app、batchを問わず、コードを作成、修正または確認する場合は、対象バージョンで承認済みのコーディング規約を必ず参照して下さい。

  - コード変更前に、共通規約と変更対象の拡張子・言語に対応する規約を全文確認し、参照したファイルを提示して下さい。
  - 規約の一部だけを確認して、コーディング規約全体を確認済みとしてはいけません。
  - 実装前に、各規約の章・項目について今回の変更への適用有無を判定して下さい。
  - 実装後に、追加・変更した全差分を適用対象となる全規約と照合して下さい。自動確認できない命名、コメント、配置、空行、既存踏襲等も目視確認して下さい。
  - 確認結果には、規約ファイル、章・項目、適用有無、判定、確認根拠を記録して下さい。
  - レビューやユーザ指示によりコードを再修正した場合は、再修正した差分について規約確認をやり直して下さい。
  - 未確認項目または規約違反が1件でもある場合は、コード作成・修正・確認を完了扱いにしてはいけません。
  - コーディング規約の確認だけを目的として、変更対象外の既存コードを一括修正してはいけません。

  対象バージョンにコーディング規約が存在しない、配置が不明、内容が矛盾する、または適用判断ができない場合は、コード変更を開始せずユーザへ報告して下さい。

### 開発種類

  作業は、通常開発、簡易開発および分析の3種類に分かれます。
  - 通常開発: 要件定義から設計、実装、確認までを段階的に行う開発です。開発種類として `batch`、`app`、`class` を使用します。
  - 簡易開発: 軽微な修正などを簡略化した手順で行う開発です。開発種類として `quick_fix` を使用します。

### UIデザイン追加分類

  参照画像、モックアップ、ワイヤーフレーム、画面構造またはレスポンシブレイアウトを扱う`app`開発では、追加分類`ui-design`を適用し、`.rules/dev/app/ui/rules_app_ui_design.md`を必ず参照して下さい。
  `ui-design`は独立した開発種類ではなく、`app`の手順1〜10へ追加する必須ルールです。
  参照資料がある場合、機能維持とレイアウト維持を分け、再現度、UI要件ID、実装前プレビュー承認、画面幅別スクリーンショットおよびユーザの最終目視承認を管理して下さい。
  - 分析: GitHub Actionsを原則の実行基盤、Gitを管理基盤として、一括分析を行います。作業種類として `analyze` を使用します。

### 通常開発

  下記ファイルを順番に作成します。
  {filename}はコードファイル名、{n}はバージョン、{m}はリビジョンになります。
  該当する手順のルールファイルを参照しながら作成を行って下さい。
  - 参照可: 当該工程ルール、共通ルール、直前工程で承認済みの成果物
  - 参照不可: 未承認の途中成果物、他工程の未使用ルール
  - 例外: 通常開発の手順10（最終確認）では、仕様書、手順1〜9で承認済みの全成果物、および各確認結果を参照可とします。

  開発を開始する前に、対象バージョンの格納フォルダを作成します。
  手順3〜10で作成する成果物は、すべてこのフォルダ内に格納します。
  手順1〜2で作成する仕様書、および仕様確認結果は、コード単位ではなくプロジェクト全体を対象とするため、プロジェクト直下の`.document/v{n}.{m}/`フォルダに格納します。
  `.document`フォルダまたは対象バージョンのフォルダが存在しない場合は、仕様書を作成する前に作成します。
  `.document`フォルダはGit管理対象とします。空フォルダとして保持する必要がある場合は、`.document/.gitkeep`を作成します。

  フォルダ名は `{filename}_v{n}.{m}` とします。
  例: `alert_rci_v21.1`

  各手順が終わった時点でユーザに確認を取って下さい。
  手順1が終わったらユーザに確認を取り、問題なければ手順2に進みます。
  手順2が終わったらユーザに確認を取り、問題なければ手順3に進みます。
  以下、同様です。
  処理中に矛盾が見つかった場合は、処理を終了してユーザに報告して下さい。

### 変更区分の独立判定

  `[ADD]`、`[MOD]`、`[DEL]`、`[KEEP]` は、仕様書、基本設計の処理、詳細設計の処理・関数・ロジック・変数、コードの各管理対象について個別に判定して下さい。

  - 上位工程の変更区分を、下位工程の管理対象へ機械的に継承してはいけません。
  - 基本設計の処理 `[Sxxx]` が `[MOD]` でも、その処理から呼ばれる既存関数自体を変更しない場合、当該関数 `[Fxxx]` または `[Txxx]` は `[KEEP]` として下さい。
  - 既存コードを実際に変更する関数だけを `[MOD]`、新規作成する関数だけを `[ADD]`、削除・廃止する関数だけを `[DEL]` として下さい。
  - 処理フローに関係するだけでコードを変更しない関数を、`[MOD]` の実装対象として扱ってはいけません。
  - 詳細設計では現行コードを確認し、実在するファイル、関数、呼び出し元、呼び出し先と変更予定箇所を特定した上で変更区分を決定して下さい。
  - 実装時に変更区分または対象関数の誤りを発見した場合はコード変更を停止し、詳細設計と詳細設計確認を補正してユーザの承認を得てから再開して下さい。

  各ファイル作成後、ログを`.rules/log/rules_{dev}.log`に記述します。
  ファイル作成時に気になることや懸念事項などあれば、質問して構いません。

  `{dev}`は設計書の種類を示しており、
  - batch : バッチ処理用の設計書
  - app   : アプリケーション用の設計書
  - class : クラス設計書（作成中）

  があります。
  最初に、どの設計書を使用するかを確認して下さい。
  以降、その設計書を使用して設計を進めます。
  ルールファイルは、`.rules/dev/{dev}/`フォルダにあります。
  下記の10工程は `app` と `batch` に適用します。`class` の工程変更は保留とし、既存のclassルールに従って下さい。

  |手順|種類|ルールファイル|出力ファイル名|
  |---|---|---|----|
  |1|仕様書作成|`rules_{dev}_1_spec.md`|プロジェクト直下の`.document/v{n}.{m}/`フォルダの `00_index.md`、`01_差分仕様.md`、および項目別仕様書|
  |2|仕様確認|`rules_{dev}_2_spec_confirm.md`|プロジェクト直下の`.document/v{n}.{m}/99_仕様確認.md`|
  |3|要件定義書|`rules_{dev}_3_request.md`|`{filename}_v{n}.{m}_3_request.md`|
  |4|基本設計書|`rules_{dev}_4_base.md`|`{filename}_v{n}.{m}_4_base.md`|
  |5|基本設計書確認|`rules_{dev}_5_base_confirm.md`|`{filename}_v{n}.{m}_5_base_confirm.md`|
  |6|詳細設計書|`rules_{dev}_6_detail.md`|`{filename}_v{n}.{m}_6_detail.md`<br>`{filename}_v{n}.{m}_6_detail.json`|
  |7|詳細設計書確認|`rules_{dev}_7_detail_confirm.md`|`{filename}_v{n}.{m}_7_detail.json`|
  |8|コード|`rules_{dev}_8_code.md`|`{filename}_v{n}.{m}.{code_ext}`|
  |9|コード確認|`rules_{dev}_9_code_confirm.md`|`{filename}_v{n}.{m}_9_code_confirm.md`|
  |10|最終確認|`rules_{dev}_10_final_confirm.md`|`{filename}_v{n}.{m}_10_final_confirm.md`|

### 簡易開発

  簡易開発の手順を以下に示します。

  簡易開発は、軽微な修正、既存仕様の範囲内の不具合修正、文言修正、ログ修正、コメント修正、既存処理の小規模な条件変更などを対象とします。
  仕様変更および仕様書の修正を伴う作業は対象外とし、通常開発を使用します。
  簡易開発では仕様書を作成、変更、削除してはいけません。
  簡易開発の指示があった場合は、こちらに沿って修正を行って下さい。

  下記ファイルを順番に作成します。
  {filename}はコードファイル名、{n}はバージョン、{m}はリビジョンになります。
  該当する手順のルールファイルを参照しながら作成を行って下さい。
  - 参照可: 当該工程ルール、共通ルール、直前工程で承認済みの成果物
  - 参照不可: 未承認の途中成果物、他工程の未使用ルール
  - 例外: 簡易開発の手順3（コード確認）では、既存仕様書、手順1〜2で承認済みの全成果物、および動作確認結果を参照可とします。

  簡易開発を開始する前に、対象バージョンの格納フォルダを作成します。
  手順1〜3で作成する成果物は、すべてこのフォルダ内に格納します。

  フォルダ名は `{filename}_v{n}.{m}` とします。
  例: `alert_rci_v21.1`

  各手順が終わった時点でユーザに確認を取って下さい。
  手順1が終わったらユーザに確認を取り、問題なければ手順2に進みます。
  手順2が終わったらユーザに確認を取り、問題なければ手順3に進みます。
  以下、同様です。
  処理中に矛盾が見つかった場合は、処理を終了してユーザに報告して下さい。
  仕様変更の必要性が判明した場合は作業を停止し、通常開発へ切り替えるかユーザへ確認して下さい。
  ユーザが承認した場合のみ、通常開発を手順1から開始して下さい。ユーザの承認を得ずに切り替えてはいけません。

  各ファイル作成後、ログを`.rules/log/rules_quick_fix.log`に記述します。
  ファイル作成時に気になることや懸念事項などあれば、質問して構いません。

  簡易開発では、app / batch 共通のルールとして `.rules/dev/quick_fix/` フォルダ配下のルールファイルを参照します。

  原則として、簡易開発を行う場合はリビジョンを上げます。

  |手順|種類|ルールファイル|出力ファイル名|
  |---|---|---|----|
  |1|修正内容の要件|`rules_quick_fix_1_request.md`|`{filename}_v{n}.{m}_1_request.md`|
  |2|コード修正|`rules_quick_fix_2_code.md`|`{filename}_v{n}.{m}.{code_ext}`|
  |3|コード確認|`rules_quick_fix_3_code_confirm.md`|`{filename}_v{n}.{m}_3_code_confirm.md`|

### 分析

  分析では、条件と全体ワークフローを事前に確定・承認し、その後は重大な停止条件がない限り追加確認を行わず一括実行します。
  GitHub Actionsを原則として使用し、コードでの解析が困難な場合は承認済みworkflowに従ってChatGPT分析または併用分析を行います。

  分析成果物は、対象リポジトリで定めた分析用フォルダへ格納します。
  public/privateの2リポジトリを使用する場合、非公開の条件、コード、入力、詳細結果およびChatGPT分析記録はprivate側を正本とします。
  各工程の成果物作成後、ログを`.rules/log/rules_analyze.log`に記述します。

  |手順|種類|ルールファイル|主な出力|
  |---|---|---|---|
  |1|分析条件定義|`rules_analyze_1_request.md`|`{analysis}_v{n}.{m}_1_request.md`|
  |2|全体ワークフロー設計|`rules_analyze_2_workflow.md`|`{analysis}_v{n}.{m}_2_workflow.md / .json`|
  |3|分析条件・ワークフロー確認|`rules_analyze_3_workflow_confirm.md`|`{analysis}_v{n}.{m}_3_workflow_confirm.md`|
  |4|Actions・分析処理作成|`rules_analyze_4_implementation.md`|workflow、分析コード、`{analysis}_v{n}.{m}_4_implementation.md`|
  |5|一括分析実行|`rules_analyze_5_execute.md`|`{analysis}_v{n}.{m}_5_result.md / .json`、manifest、checkpoint|
  |6|分析結果確認|`rules_analyze_6_result_confirm.md`|`{analysis}_v{n}.{m}_6_result_confirm.md`|

  手順3のユーザ承認後は、停止条件に該当しない限り手順4と手順5を一括して進めます。
  手順6で修正が必要と判明しても、自動的にコードや仕様を変更せず、app、batchまたはquick_fixへの切替についてユーザ確認を取って下さい。
