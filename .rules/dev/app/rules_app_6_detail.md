## 詳細設計書

### 詳細設計書の内容

  基本設計書の各処理`[Sxxx]`について、下記を記述します。
  基本的には、1つの処理につきメインとなる関数は1つとし、フロントエンドのイベントハンドラや、バックエンドのAPIエンドポイントなどを記述します。
  
  **つまり、各処理`[Sxxx]`ごとに、個別に下記の項目1 - 7を作成します。**
  各処理をまとめて項目を作成してはいけません。


  |no|項目|説明|
  |----|----|----|
  |1|処理概要|基本設計の処理ID（Sxxx）に基づき、何を実現する関数かを記述します。|
  |2|メイン関数|[Fxxx] IDを付与した、処理の入り口となるメイン関数を記述します。|
  |3|引数|引数一覧の名称、データ型、説明をテーブル形式で記述します。各引数には[Ixxx] IDを付与します。|
  |4|戻り値|戻り値一覧の名称、データ型、説明をテーブル形式で記述します。各戻り値には[Oxxx] IDを付与します。|
  |5|外部変数|参照している外部変数一覧の名称、データ型、説明をテーブル形式で記述します。各戻り値には[Vxxx] IDを付与します。|
  |6|処理フロー|メイン関数から呼び出されるサブルーチンやロジックの流れをステップ単位で記述します。|
  |7|特記事項|非同期処理、エラーハンドリング、セキュリティ上の注意点などを記述します。|

### 補助関数

  補助関数についても、関数ID`[Txxx]`を割り当て、各処理`[Sxxx]`と同様の記述を行います。

### [Fxxx], [Txxx]の詳細

  - [Fxxx] は主関数IDとし、[Txxx] は補助関数IDとする。
  - 1つの関数に付与するIDは [Fxxx] または [Txxx] のどちらか一方のみとする
  - [Fxxx] は画面更新、API応答、主要処理などの公開的な責務を持つ関数に付与する
  - [Txxx] は [Fxxx] から呼ばれる補助処理用の関数に付与する
  - [Txxx] を直接エントリーポイントとして扱ってはならない
  - 同一関数に [Fxxx] と [Txxx] を併記してはならない
  - F = publicメソッド相当、T = privateメソッド相当と解釈します。
  - T/F は別軸ではなく、関数種別を表す排他的なID分類である

### 詳細設計書作成ルール

#### 1. ID体系の追加定義
詳細設計では、以下のIDを必ず割り当てて下さい。
- `[Sxxx]`: 処理内容
- `[Txxx]`: 補助関数
- `[Lxxx]`: 処理ロジック・アルゴリズムの各ステップ
- `[Fxxx]`: 関数（Functions）
- `[Ixxx]`: 関数の引数
- `[Oxxx]`: 関数の戻り値
- `[Vxxx]`: 参照外部変数

#### 2. コンポーネント・カタログの外部化
詳細設計書（Markdown）が肥大化するのを防ぐため、以下の運用を行います。
- **Markdown:** 処理フロー（L-ID）を中心に記述し、各 L-ID の中で関連する F-ID / V-ID を参照する。
- **JSON (`{filename}_v{n}.{m}_6_detail.json`):** 全ての `[Sxxx]`, `[Txxx]`, `[Lxxx]`, `[Ixxx]`, `[Oxxx]`, `[Vxxx]` および `[Fxxx]` の定義をリスト化して出力する。
- 関数の定義には、ファイル別関数一覧と照合できるよう対象ファイルの相対パスを保持する。
- **役割分担:**
  - Markdown は「処理の流れ、分岐、順序、呼び出し関係」を読むための文書とする。
  - JSON は「処理フロー・関数・変数の辞書」として扱い、名称、役割、型、引数、戻り値、使用箇所、状態を保持する。

#### 3. タグ付与対象の明確化
タグは、詳細設計書内の以下の管理対象に付与して下さい。
- `[Sxxx]`: 処理内容
- `[Lxxx]`: 処理ロジック・アルゴリズムの各ステップ
- `[Fxxx]`: 関数の定義
- `[Txxx]`: 補助関数の定義
- `[Ixxx]`: 関数の引数の定義
- `[Oxxx]`: 関数の戻り値の定義
- `[Vxxx]`: 参照外部変数

タグは以下を使用します。

```
[ADD]: 今回新規に追加する処理・関数・変数（緑色フォント併用）
[MOD]: 既存の処理・関数・変数を変更する箇所（青色フォント併用）
[DEL]: 廃止する処理・関数・変数（赤字・取り消し線併用）
[KEEP]: 前バージョンから変更せず維持する重要な処理・関数・変数（黒字のまま）
```

#### 4. 変更区分と実装対象の判定

- 基本設計の `[Sxxx]` の変更区分と、詳細設計の `[Fxxx]`、`[Txxx]`、`[Lxxx]`、`[Ixxx]`、`[Oxxx]`、`[Vxxx]` の変更区分は独立して判定して下さい。
- `[Sxxx]` が `[MOD]` であることだけを理由に、配下の関数・引数・戻り値・変数・ロジックを一律に `[MOD]` としてはいけません。
- 詳細設計を作成する前に現行コードを確認し、変更する実在のファイルと関数を特定して下さい。
- 既存関数のコード自体を変更しない場合は、処理フローへ関係していても当該関数を `[KEEP]` として下さい。
- 呼び出し元だけを変更する場合は呼び出し元を `[MOD]`、呼び出される既存関数を `[KEEP]` として下さい。
- 新規関数は `[ADD]`、既存関数の変更は `[MOD]`、廃止は `[DEL]`、無変更は `[KEEP]` として下さい。
- 概念上の処理名を実装関数名として作成せず、実在する関数名または新規作成する正式な関数名を記述して下さい。
- 実装関数対応表を作成し、各 `[ADD]`・`[MOD]` のIDについて、対象ファイル、対象関数、変更内容を明記して下さい。
- 処理へ関係するが変更しない関数は、実装関数対応表で「変更なし」と明記して下さい。

#### 5. 実装ファイル構成

- 詳細設計書に「実装ファイル構成」を作成し、実装対象を含むディレクトリ構成をツリー形式で記載して下さい。
- 新規作成、変更、削除する全ファイルを記載し、各ファイルに `[ADD]`、`[MOD]`、`[DEL]` の変更区分と責務または変更概要を併記して下さい。
- 配置関係の理解に必要な親ディレクトリと参照対象も記載して下さい。参照するだけで変更しないファイルには `[KEEP]` を付与して下さい。
- プロジェクトルートからの相対パスを使用し、仕様書の「フォルダ構成・ファイル構成」と一致させて下さい。
- ファイル単位の変更区分と、ファイル内の関数単位の変更区分を混同してはいけません。
- ツリーとは別に、変更区分、対象ファイル、責務または変更概要を示す「ファイル変更区分」の表を作成して下さい。

#### 6. ファイル別関数一覧

- 対象ファイルごとに小見出しと表を分けて下さい。複数ファイルの関数を一つの表に混在させてはいけません。
- 小見出しには、対象ファイルの相対パスと記載する関数数を明記して下さい。
- 新規作成ファイルは実装する全関数を記載して下さい。
- 既存ファイルは今回 `[ADD]`、`[MOD]`、`[DEL]` となる関数と、変更内容の理解に必要な `[KEEP]` 関数を記載して下さい。
- 各表には、少なくとも `ID`、`区分`、`関数名`、`戻り値`、`引数`、`処理内容` を記載して下さい。公開範囲を持つ言語では `公開範囲` も記載して下さい。
- 原則として実装後のファイル内の並び順で記載して下さい。
- 実装関数対応表、各 `[Sxxx]` の定義、コンポーネント・カタログ（JSON）と、ID、区分、関数名、対象ファイルを一致させて下さい。
- 関数を持たない対象ファイルは、関数一覧を作らず「該当なし」と理由を明記して下さい。

#### 7. DB物理設計

- テーブルを新規作成、変更または削除する場合は「DB物理設計」を作成して下さい。対象がない場合は「該当なし」と明記して下さい。
- DBエンジン、文字コード、照合順序、型、命名、外部キー、トランザクション、排他制御、および機密情報の保存に関する共通方針を記載して下さい。
- テーブルごとに小見出しを分け、変更区分、物理名、論理名、用途、およびカラム定義を記載して下さい。
- カラム定義には、少なくとも `カラム`、`型`、`NULL`、`キー・制約`、`デフォルト値`、`説明` を記載して下さい。
- 主キー、複合主キー、一意制約、インデックス、外部キーまたは論理的な参照関係、初期データ、保持・削除方針、およびテーブル固有の整合性規則を明記して下さい。
- 新規テーブルは全カラムと全制約を記載して下さい。既存テーブルの変更は差分だけでなく変更後の完成形を記載して下さい。
- 削除するテーブルまたはカラムは、削除理由、影響範囲、データ移行または退避方針を記載して下さい。
- DDLを作成する場合は実装ファイル構成にも掲載し、テーブル名、カラム、型、NULL、キー・制約、デフォルト値、インデックス、DBエンジンおよび文字コードをDB物理設計と一致させて下さい。

#### 8. 詳細設計書の分割

- 詳細設計書が大きくなる場合は、本体、実装ファイル構成、ファイル別関数一覧、DB物理設計など、内容単位でMarkdownを分割できます。
- 本体に分割ファイル一覧、内容、参照順序、および相対リンクを記載し、各分割ファイルから本体へ戻る相対リンクを記載して下さい。
- 本体と全分割ファイルのバージョンおよびリビジョンを一致させて下さい。
- IDは分割ファイルを含む詳細設計全体で一意にし、同じ定義を複数ファイルへ重複記載してはいけません。
- `[ADD]`、`[MOD]`、`[DEL]`、`[KEEP]` の集計は全分割ファイルを対象として下さい。
- コンポーネント・カタログJSONは、分割された全Markdownの定義を統合した一つの正本として出力して下さい。
- 詳細設計確認では、本体と全分割ファイルを一つの成果物として確認して下さい。

#### 9. 出力ファイル
- `{filename}_v{n}.{m}_6_detail.md`
- `{filename}_v{n}.{m}_6_detail.json`
- 分割する場合: `{filename}_v{n}.{m}_6_detail_{内容}.md`


### 詳細設計書の作成手順

  下記の順番で作成します。

  1. 対応する基本設計書（`_4_base.md` および `_5_base_confirm.md`）と同じバージョン・リビジョンであることを確認します。
  2. 基本設計書と同じバージョン・リビジョンのファイルをコピーします。
  3. タグを付与します。各項目（処理フローの各ステップ、関数定義、変数定義）の先頭に、必ずタグを記述して下さい。
  4. 現行コードと照合し、各タグを管理対象単位で独立して判定します。上位工程のタグをそのまま複製してはいけません。
  5. 仕様継承の義務: 前バージョンの処理・関数・変数を省略せず、既存の全ての項目に [KEEP] [MOD] [DEL] のいずれかを付与して全文を維持すること。新規追加の項目には [ADD] を付与すること。[DEL] の項目は本文から削除せず、取り消し線付きで残し、実装対象からは除外すること。
  6. 集計レポートを設計書末尾に出力します。タグごとの件数を表形式で必ず記述して下さい。

  レポートの例
  |タグ|件数|内容（要約）|
  |---|---|---|
  |[ADD]|2件|RCI期間設定の追加、ログ出力フラグの追加|
  |[MOD]|1件|アラート判定閾値の変更|
  |[DEL]|1件|不要になった旧描画ロジックの削除|
  |[KEEP]|12件|移動平均計算、UIカラー設定、etc...|


### 処理の流れ

  - 基本的には下記の様なコードを想定して、処理の流れを作成して下さい。

  - サンプルコード
    - 下記のようにメインとなる変数を関数単位で受け渡すように書くこと。
    - ローカル変数は適時使用すること。
    - コメントは詳細に書くこと。
    - 関数単位でログを出力できるようにすること。
    - ログ出力は `isOutputLog` 変数で設定できるようにすること。
    ```text
    //処理1
    def myFunkA(listA)

    //処理2
    def myFunkB_1(listB, param_1)
    def myFunkB_2(listB)

    //処理3
    def myFunkC(listC, param_2)

    //メイン処理
    def main()

        param_1 = "sample"
        param_2 = "sample"

        listA = ["a", "b", "c"]

        listB = myFunkA(listA)

        listC_1 = myFunkB_1(listB, param_1)
        listC_2 = myFunkB_2(listB)

        listResult = myFunkC(listC_1, listC_2, param_2)

    call main()
    ```

### UIデザイン追加詳細

UIデザイン追加分類を適用する場合、UI要件IDとHTML、CSS、JavaScript、画像の対応、DOM順序、主要クラス、PC・モバイルの表示条件、主要寸法、余白、重なり順、画像トリミング、状態表示、既存イベントの保持、実装しない参照要素の理由および画面幅別確認方法を記載して下さい。
