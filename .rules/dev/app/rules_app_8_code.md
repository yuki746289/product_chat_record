## コード設計書

詳細設計書（`_6_detail.md / .json`）および実装用統合JSON（`_7_detail.json`）に基づき、以下のルールを厳守してコードを実装して下さい。
開発方針やロジックに矛盾・不明点が見つかった場合は、実装を進める前に必ずユーザに報告し、指示を仰いで下さい。

### 1. 実装開始時の宣言（プレ・フライト・チェック）
実装を開始する直前に、以下の内容を回答として提示して下さい。
- **ターゲットJSONの確認:** 参照する `{filename}_v{n}.{m}_7_detail.json` のバージョン。
- **変更箇所のリストアップ:** JSON内の `[ADD]` および `[MOD]` タグが付いた全項目（L/F/T/I/O/V ID）を列挙し、それらを「どのファイル・どの関数」で実装するかを宣言して下さい。
- **現行コードとの再照合:** `[ADD]` は新規作成、`[MOD]` は既存コード変更、`[KEEP]` は無変更になっていることを、実装開始前に現行コードと照合して下さい。
- **変更不要関数の除外:** 処理フローに関係していても、コード自体を変更しない関数を実装対象へ含めてはいけません。
- **設計誤り時の停止:** `[ADD]`・`[MOD]` の対象に変更不要な関数が含まれる、または必要な変更関数が設計にない場合は実装を開始せず、手順6・7へ戻って設計を補正し、ユーザの承認を得て下さい。
- **コーディング規約の確認:** 対象バージョンの共通規約と、変更対象の拡張子・言語に対応する規約を全文確認し、参照ファイルを提示して下さい。
- **適用規約の判定:** 各規約の章・項目について今回の変更への適用有無を判定し、未確認項目がないことを確認して下さい。

### 2. IDコメントの埋め込みルール
詳細設計との整合性を確保するため、コード内の適切な箇所に以下のコメントを**必須**で記述して下さい。

| ID種別 | 記述場所 | 記述例 |
| :--- | :--- | :--- |
| **[Lxxx]** | 処理ロジック・アルゴリズムの各ステップの開始位置 | `// [L101] EMA計算ロジック開始` |
| **[Fxxx]** | 関数の**定義箇所（宣言部分）**の直前 | `// [F101] データ取得メイン関数` |
| **[Txxx]** | 関数の**定義箇所（宣言部分）**の直前 | `// [T101] データ変換補助関数` |
| **[Ixxx]** | 引数の**宣言・初期化箇所** | `// [I101] 入力データリスト` |
| **[Oxxx]** | 戻り値の**宣言・初期化・返却箇所** | `// [O101] 計算結果の戻り値` |
| **[Vxxx]** | 外部変数・定数の**参照または更新箇所** | `// [V101] ログ出力フラグを参照` |

### 3. コード品質・安全性の担保
- **不変条件（Invariants）の保護:** `[KEEP]` タグが付いた既存ロジックを修正・削除してはいけません。実装完了後、既存の挙動が維持されているか再確認して下さい。
- **差分範囲の確認:** 実装完了後、`[ADD]`・`[MOD]` に対応するファイル・関数だけに差分があり、`[KEEP]` の関数に差分がないことを確認して下さい。
- **規約全体の差分照合:** 追加・変更した全差分を、適用対象となるコーディング規約の全項目と照合して下さい。一部の規約だけを確認して「規約確認済み」としてはいけません。
- **目視確認の必須化:** 自動確認結果だけで合格とせず、命名、コメント、配置、インデント、空行、既存踏襲等の自動判定できない項目も目視確認して下さい。
- **再修正時の再確認:** レビューまたはユーザ指示でコードを再修正した場合は、再修正した全差分について適用規約の判定と照合をやり直して下さい。
- **未確認時の完了禁止:** 未確認項目または規約違反が1件でもある場合は、実装完了としてはいけません。
- **引数の変数化:** 新規・変更コードでは、業務上の意味を持つリテラル、演算式、文字列連結、プロパティ・配列要素、関数結果を引数へ直接渡さず、変数へ格納してから渡して下さい。呼び出し先と意味が同じ場合は、定義側と同じ変数名を使用して下さい。
- **戻り値の変数化:** 新規・変更コードでは、関数結果、プロパティ・配列要素、演算式、リテラルを直接 `return` せず、戻り値を表す変数へ格納してから返して下さい。薄い委譲メソッドも同様です。
- **例外の限定:** 値を返さない `return;`、Map/Objectのキー、言語・フレームワーク上の固定記述などは例外とします。対象ファイルまたは同一分類の周辺コードで規約と異なる書き方が確立されている場合は、既存コードとの統一を優先して周辺の書き方に合わせて下さい。単発の記述だけで判断せず、前後を含む複数の関数で同じ形式が使われていることを確認して下さい。その他の例外は周辺実装、詳細設計、ユーザー指示を確認し、理由を説明できる場合だけ使用して下さい。この確認だけを目的に `[KEEP]` の既存コードを一括修正してはいけません。
- **ログ出力制御:** 共通変数 `isOutputLog` （詳細設計で定義されている場合）に従い、関数単位で処理の開始・終了・エラーログを出力できるようにして下さい。
- **エラーハンドリング:** 異常系が定義されている場合、詳細設計のステップ（[Lxxx]）に沿って例外処理を実装して下さい。

### 4. ヘッダー情報の記述
各ソースファイルの先頭には、必ず以下の情報を詳細に記載して下さい。

```text
/**
 * 更新日時: yyyy/mm/dd
 * 処理概要: [Sxxx] に対応する処理の概要
 * 前回バージョンとの違い:
 * - [ADD]: 新規追加した機能
 * - [MOD]: 変更したロジック
 * - [DEL]: 廃止・コメントアウトした箇所
 */
```

### 5. 環境・言語固有の制約
  - 原因調査で分からないことなどがあれば、web検索で調べること。

  - 日本語の文字化けについて
    - PowerShell スクリプト（`.ps1`）に日本語を含める場合は、必ず UTF-8 with BOM で保存すること。
    - Windows PowerShell 5.x では BOM なし UTF-8 の `.ps1` が既定コードページで解釈され、文字化けすることがあるため、BOM なしで保存しないこと。
    - 日本語をファイルへ自動追記する処理を追加または修正した場合は、出力先ファイルで文字化け有無を必ず確認すること。

  - コードの最初に「更新日時」、「処理概要」、「前回バージョンとの違い」を詳細に記載すること。

  - 記法はキャメルケースを使用すること。

  - 命名規則は下記に沿うこと
    - 変数の命名規則
      |種類|プレフィックス|例|
      |------|-----|----|
      |リスト|list|listData|
      |マップ|map|mapUser|
    - 関数の命名規則
      |プレフィックス|意味|例|
      |-------|-----|----|
      |select |データを取得する|selectData()|
      |regist |データを登録する|registData()|
      |delete |データを削除する|deleteData()|
      |update |データを更新する|updateData()|
      |refresh|画面などを更新する|refreshUserTable()|

### UIデザイン追加実装

UIデザイン追加分類を適用する場合、実装開始前に参照資料、再現度、UI要件ID、承認済みプレビュー、詳細設計および素材が揃っていることを確認して下さい。UI要件を共通部品の追加など一部だけへ縮小せず、既存機能を保持したまま承認済みレイアウトを実装して下さい。
