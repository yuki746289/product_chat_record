# 数値・大量データ処理の性能最適化ルール（v13）

## 目的・対象
数値解析、バックテスト、ETL、集計、特徴量生成、長時間batch／分析／app処理の新規設計・改修・高速化に適用する。短い表示文言変更等、性能への影響がない作業では「対象外：理由」を記録し、不要な計測を強制しない。

**第一原則：結果の正しさ・監査可能性・安全性を優先し、その範囲内で実測最適な実装を採用する。** 単一ライブラリへの一律移行を禁止する。

## P01 実装前の要求・現状把握
- 対象関数／pipeline／対象母集団、入力ファイル、原本SHA256、出力契約、既存成功Run/artifact、所要時間・ピークRSS・タイムアウト・費用・ボトルネックを整理する。
- 性能目標は測定可能な値（例：中央値、p95、ピークメモリ、対象件数、完了可能性）で定義し、事前値がなければ未計測とする。目標時間を推測で「達成」としない。
- profiler／部分タイムスタンプ／フレーム数などで最も重い部分を特定する。単純なtimeout延長を初期対策にしてはいけない。
- 既に保存した成功artifactは入力・証拠として再利用し、ユーザーの許可なく元の大規模計算を再実行しない。

## P02 技術選択：pandas / NumPy / Polarsなど
| 候補 | 適用を優先検討する処理 | 採用前に検証する課題 |
|---|---|---|
| pandas | 既存契約との互換、複雑なindexや少量データ | Pythonループ、行単位apply、コピー・groupbyの過剰利用 |
| NumPy | 大量のブールマスク、共通配列キャッシュ、反復数値計算、bincount | 欠損/NaN/inf、dtype/桁、インデックスと行順対応 |
| Polars | 列指向読込、group_by、lazy/streaming、並列な表変換 | nullとNaN、並び順（sort指定）、型変換、文字列、浮動小数点集約順序 |
| その他（Numba/Arrow/SQL等） | 主要候補では性能・資源要件を満たせない場合 | 追加依存、再現性、配布・runner環境、数値契約 |

- 同じ処理・同じ入力・同じ出力契約で候補を比較する。「Polarsは常に速い」「NumPyは常に速い」と決めつけない。
- キャッシュ／事前配列化／不要コピー削減／ベクトル化／スキャン回数削減を、shard追加より先に検討する。
- 最速であっても出力不一致がある方式は採用しない。差が僅少・RAM/保守負荷が増す場合は既存実装維持を許す（理由を記録）。

## P03 公平なベンチマーク
- 可能な限り同一CPU/runner・Python/依存バージョン・スレッド上限・入力SHA・行数・列・データ型・ウォームアップ条件を使用する。
- 性能代表データで3回以上独立測定し、中央値とばらつき（p95、最悪値等）・ピークRSS・CSV読込・前処理・演算・出力時間を分ける。再実行不可の大計算は既存ログ等で代替し、測定範囲を限定と表示する。
- マイクロベンチマークを全体pipeline高速化と混同しない。高速化比は同条件実測値から計算する。
- 小標本・実条件・境界条件・全件の段階で確認し、過大な全件実行を何度も繰り返さない。ベンチマークでprivateデータを公開しない。

## P04 数値同値・回帰（必須品質ゲート）
- 同一母集団とinput SHAに対し、行数、列名と順序、キーの集合と一意性、条件ID、銘柄/日時、文字列/分類値、NaN/null/inf、0件、境界値、期間キー、マスク全行、方向性、正解率/損益等の契約を検証する。
- 契約上順序が意味を持つ場合は行順まで一致。キー比較が許される場合も、並べ替えの根拠と複合キー一意性を検証する。
- 非数値の差・条件ID差・行欠損は許容しない。数値許容誤差は事前承認値のみを使用し、後から拡大しない。floatの丸め/欠損値処理/集約順による差を記録する。
- Look-ahead bias・シグナル抽出条件・特徴量算出・既存出力契約が変わった場合は最適化とみなさず仕様変更ゲートに戻す。
- 途中stageのチェックポイント移送PASS ≠ 新Producerの全数値計算PASS。成功ジョブのconclusionだけを最終結果に使わず、監査JSONの中身を照合する。

## P05 長時間処理と回復可能性
- 実測45分超、過去timeout/cancel、ジョブ時間枠の60%超、分割可能な独立計算がある場合は単一job継続を原則禁止し、shard/stage/checkpoint設計に切り替える（対象リポジトリのより厳しい規則を優先）。
- 分割は元計算を変えない処理境界で行い、shard入力と結果にSHA/範囲/件数/重複・欠落・statusを記録し、成功shardを再実行しない。
- stage例：保存入力ゲート→Semantic候補→安定性→OR→CSV組立→独立数値QA→HTML QA。対象によって該当しないstageは理由を残す。
- 予想完了時刻は実測から算出し、**タイムアウト時刻を正常終了予測時刻として報告しない**。予測不能なら不明とする。

## P06 セキュリティ・変更権限
- Productionロジック、原本、成功済みCSV/HTML/artifact、releaseを無断変更・上書き・再生成しない。生成・計測は隔離された一時領域で行う。
- Public runnerへprivateの元CSV・特徴量・出力・秘匿コードをartifact/ログ/cacheとして出さない。公開可な集約メタデータのみ許可リスト方式で保存する。
- Workflow変更・再実行・commit・push・マージ・deployは対象リポジトリ固有の明示承認ゲートに従う。本ルールは承認を代替しない。

## P07 完了条件・証拠
- `performance_optimization_checklist.md`の各必須項目がPASSまたは理由付きN/A。NG・未確認が残れば最終PASS不可。
- 記録すべきもの：対象commit/Run/artifact、入力・実装SHA、環境、旧/新時間・RSS、差分、品質監査、拒否した候補、採用理由、残リスク、再開位置、ユーザー承認範囲。
- 対象関数の微小検証だけ通った場合は「限定PASS」。全件・全producerの完了を偽らない。
